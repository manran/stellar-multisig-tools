The public API is network-deployment bound and protocol namespaced.

```text
Mainnet: not yet publicly available
Testnet: https://api-testnet.multisig.tools/stellar
```

The `/stellar` segment is the protocol namespace. Mainnet/Testnet isolation is a deployment boundary, not a request parameter.

## Discover the contract

```bash
curl -sS https://api-testnet.multisig.tools/stellar/operations
curl -sS https://api-testnet.multisig.tools/stellar/openapi.json
```

Each registry entry's `schema.href` identifies the OpenAPI document and `schema.pointer` identifies its exact logical operation in `x-multisig-operations`. Resolve that pointer instead of choosing a branch of the shared HTTP path. Its parameters, security, request body, success responses, dispatch defaults, and retry policy apply to the selected operation.

The registry's `apiVersion` and OpenAPI `info.version` identify the same contract revision. Individual operation wire versions remain stable. The public discovery documents support ETag revalidation and HEAD; private state is never cached publicly.

## Core rules

**Network-bound origin:** use the deployment that owns the selected network. A Request/Intent cannot be switched to another network by URL parameter or wallet default.

**Idempotency:** only machine Request and Intent creation (`proposal.create`, `integration.request.create`, `contract.intent.create`, `integration.intent.create`) requires a stable `Idempotency-Key`. Retry the same accepted input with the same credential and key; changed input conflicts. One-time Agent pairing and Testnet Integration Profile issuance do not have this replay guarantee. Profile creation rejects this header.

**Job projection:** follow `nextActions` and `actionCalls` for Integration jobs, or `nextActions[].operationId` and `bodyDefaults` for signer Agents. Resolve the operation contract and respect its access requirements. `reviewRequired: true` on an action requires an explicit caller decision after reviewing the resolved prior attempt; it is not a new authorization grant. A Classic task with `state=execution_unknown` is not a failed payment: inspect its `executionOutcome`; the owning Integration reconciles the original hash. An external Stellar submission is not an MST API operation.

**Retry:** apply the exact operation's `retry.onError` rule first, then `retry.onHttpStatus`, then `retry.defaultError`. If no response was received, use `retry.transportFailure`. Do not infer that a timeout means a write did not commit. For execution reconciliation, apply `retry.onOutcome` to the validated result. A retry strategy never grants permission to sign or submit.

**Webhook:** receive → verify → deduplicate event id → GET canonical Request/Intent/Job → act from current state.

## Inspect your Integration Profile

Call `GET /integration-execution` with the Integration bearer credential. The `configuration` field contains only the owning service's permitted accounts, contract methods, execution modes, profile preferences and webhook configuration. It excludes all secrets and secret hashes. An existing credential is never recovered or silently replaced: an authorized operator must rotate it. For a disposable Testnet service, obtain approval before creating a new unique profile.

Classic and Soroban creation/inspection responses expose their respective Integration jobs with review links. A Classic job reports `waiting_preconditions` separately from signature collection.

## Webhook verification

### Register and manage delivery

Set the optional webhook object when creating a Testnet Integration Profile:

```json
{ "webhook": { "url": "https://your-service.example/mst/webhook", "enabled": true } }
```

Include this field in the existing Profile creation body, not as a separate API call. The successful response returns `webhookSecret` once (alongside `apiKey`). Store it in your server-side secret store. The URL must be a publicly reachable HTTPS endpoint; do not use a private network target.

Inspect the registered URL, enabled status and secret version using `GET /integration-execution?network=testnet`. Changing an existing URL, disabling delivery, rotating the signing secret or redelivering a terminal event requires an authorized operator via the Integration administration surface; the public self-service API cannot do these operations.

### Event and delivery contract

All notifications use event type `work.changed` and schema `multisigtools-integration-webhook-v1`. The payload is a snapshot of current work, not an immutable list of individual state transitions. For Classic work, `data.projection.type` is `classic_request` and `data.projection.request` contains the transaction hash, counts, status, reason and available terminal evidence. For Soroban work, the type is `soroban_job` and `data.projection.job` contains its current actions and evidence.

```json
{
  "schema": "multisigtools-integration-webhook-v1",
  "id": "<event-id>",
  "type": "work.changed",
  "createdAt": "2026-11-26T00:00:00Z",
  "serviceId": "your-service-id",
  "data": {
    "work": {
      "kind": "classic_request",
      "id": "<request-id>",
      "network": "testnet"
    },
    "projection": {
      "type": "classic_request",
      "request": {
        "version": 1,
        "id": "<request-id>",
        "network": "testnet",
        "transactionHash": "<64-character-hash>",
        "createdAt": "2026-11-26T00:00:00Z",
        "expiresAt": "2026-11-27T00:00:00Z",
        "contributionCount": 0,
        "signatureCount": 0,
        "status": "awaiting_signatures",
        "statusReason": "signatures_required"
      }
    }
  }
}
```

The OpenAPI `webhooks.workChanged` entry defines the payload and headers. A successful HTTP 2xx acknowledges delivery. HTTP 408, 425, 429 and 5xx, or a transport failure, are retried after 5 seconds, 30 seconds, 2 minutes, 10 minutes, 1 hour, 6 hours and 12 hours. After these seven retries the event is terminal. Other non-2xx responses fail permanently; delivery does not follow redirects. An operator can explicitly redeliver a terminal event. Never use webhook order to infer settlement.

### Verify the signature

Webhook signing uses Standard Webhooks. Verify the raw request body before JSON parsing.

```ts
import { Webhook } from 'standardwebhooks';

const rawBody = await request.text();
const headers = {
  'webhook-id': request.headers.get('webhook-id') ?? '',
  'webhook-timestamp': request.headers.get('webhook-timestamp') ?? '',
  'webhook-signature': request.headers.get('webhook-signature') ?? '',
};

const event = new Webhook(process.env.MULTISIG_WEBHOOK_SECRET!)
  .verify(rawBody, headers);

// Deduplicate event.id, then GET current canonical state.
```

MultiSig Tools may retry automatically and an operator may explicitly redeliver a terminal webhook. Redelivery keeps the same `webhook-id` / event `id`; treat it as another delivery attempt of the same event, not a new business event. Record an event as processed only after your handler has completed the work you intend to deduplicate.

## Authorization experience

| UI name | Profile value | Responsibility |
| --- | --- | --- |
| Hosted | hosted | Signers use the MST review page. |
| On my site / Native | native | Your browser handles signer UI with a scoped capability. |
| Full Headless | headless | Your service orchestrates the documented API calls. |

The profile value records the chosen integration experience. It does not grant signing authority, alter the Stellar network, or select transaction execution ownership. Credential scopes and live account policy control those independently.

## Error handling

Branch on stable error codes, not message text. See the [state and error reference](/stellar/developers/reference) and the machine-readable `x-multisig-errors` directory in OpenAPI. Validation errors can include `details.field`, `allowedValues` and `expectedType`. The operation-specific retry contract is authoritative.

| HTTP | Meaning | Caller action |
| --- | --- | --- |
| 400 | Invalid input or missing idempotency key | Fix the request; do not blind-retry. |
| 401 | Credential missing or invalid | Refresh or replace the credential. |
| 403 | Credential outside configured scope | Change scope or request. |
| 409 | Idempotency/state/network/configuration conflict | Read current state or change configuration; do not blind-retry. |
| 404 | Resource not found | Check the resource ID and deployment. |
| 410 | Expired resource or grant | Obtain a new valid grant or resource. |
| 413 | Request body too large | Reduce the request size. |
| 415 | Unsupported media type | Send application/json. |
| 429 | Rate limited | Retry with backoff. |
| 502 | Upstream interface or network response unavailable | Inspect the input and retry with backoff if temporary. |
| 503 | Dependency/storage unavailable | Retry with backoff and inspect current state. |
