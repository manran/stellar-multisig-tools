---
title: Testnet quickstart
description: Run one Hosted Classic Request end to end on Testnet.
---

Use the Testnet deployment to prove scope, authorization, execution, and status delivery before any Mainnet rollout. Prepare a funded Testnet Treasury, an eligible signer wallet, and a valid destination. Replace the example G addresses below with your own Testnet addresses before running these requests.

The public API base is:

```text
https://api-testnet.multisig.tools/stellar
```

The Hosted Human review surface remains:

```text
https://stellar-testnet.multisig.tools
```

## 1. Inspect the deployment

```bash
curl -fsS https://api-testnet.multisig.tools/stellar/runtime-config
```

Verify `fixedNetwork=testnet` and inspect `capabilities.classicManagedExecution.testnet`. Choose managed semantic payment only when that capability is true. Otherwise use prepared XDR. Decide whether MST or your service owns final submission before creating the profile.

## 2. Create a Testnet Integration Profile

```bash
curl -sS -X POST https://api-testnet.multisig.tools/stellar/integration-testnet \
  -H "Content-Type: application/json" \
  -d '{
    "serviceId": "my-testnet-app",
    "label": "My Testnet App",
    "classicSourceAccounts": ["GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAWHF"],
    "profile": { "authorizationExperience": "hosted" }
  }'
```

Use a lowercase service ID of 1–40 letters, digits or hyphens, starting with a letter or digit. Invalid IDs return HTTP 400 (`invalid_integration_service_id`); the API does not silently lowercase them.

Store the returned one-time `msi_*` credential directly in your server-side or Agent secret store. Profile creation is atomic create-only, not idempotent credential delivery; do not send `Idempotency-Key`. If the response is lost, retry the same service ID and payload. HTTP 409 `integration_service_exists` means that ID is occupied; the original key cannot be retrieved or replaced through public self-service. For a disposable Testnet profile, obtain approval to use a new unique service ID. For an existing profile that must be retained, an authorized operator must rotate its key. Never treat an occupied ID as proof that you own it.

The default profile lets MST submit the authorized Request. To own final submission yourself, include the same Treasury in `classicExternalExecutionSourceAccounts` when creating the profile. The prepared-XDR path below works without managed transaction-source channels.

## 3. Prepare and create a Classic Request

If `capabilities.classicManagedExecution.testnet` is `false`, first prepare the exact unsigned payment with your Integration credential:

```bash
curl -sS -X POST https://api-testnet.multisig.tools/stellar/payment-prepare \
  -H "Authorization: Bearer $MULTISIG_INTEGRATION_KEY" \
  -H "Content-Type: application/json" \
  -d '{"network":"testnet","sourceAccount":"GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAWHF","payments":[{"destination":"GDGV7V7UT3XDMQ3COT25VCQNJDW57WYPHSLFSAJEW2LLZDCDREWNAPXO","amount":"1","asset":{"type":"native"}}]}'
```

Create the Request with the returned `xdr` (not the semantic `payment` field):

```bash
curl -sS -X POST https://api-testnet.multisig.tools/stellar/request \
  -H "Authorization: Bearer $MULTISIG_INTEGRATION_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: payroll-test-001" \
  -d '{"network":"testnet","xdr":"<prepared-xdr>","externalReference":"payroll-test-001"}'
```

If managed execution is enabled, the following alternative creates the semantic Request directly. Choose one path, not both.

```bash
curl -sS -X POST https://api-testnet.multisig.tools/stellar/request \
  -H "Authorization: Bearer $MULTISIG_INTEGRATION_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: payroll-test-001" \
  -d '{
    "network": "testnet",
    "payment": {
      "sourceAccount": "GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAWHF",
      "payments": [{
        "destination": "GDGV7V7UT3XDMQ3COT25VCQNJDW57WYPHSLFSAJEW2LLZDCDREWNAPXO",
        "amount": "1",
        "asset": { "type": "native" }
      }],
      "memo": "Test payment"
    },
    "externalReference": "payroll-test-001"
  }'
```

The sample addresses are documentation fixtures, not funded accounts.

## 4. Open Hosted review

Use the returned Request id:

```text
https://stellar-testnet.multisig.tools/s#<request-id>
```

The `#` fragment contains the Request ID. The site reads it in the browser; `?request=...` does **not** open a Proposal. Testnet is selected by the site address, not by a `network` query parameter.

Each Treasury signer opens the Proposal, reviews the transaction, and signs with their own Stellar wallet. When the required authorization is complete, MST-managed Integration Requests can submit automatically. An authorized participant can confirm submission or retry if necessary and open the [transaction receipt](/stellar/start/sign-a-proposal#after-submission).

## 5. Read canonical status

```bash
curl -sS https://api-testnet.multisig.tools/stellar/request \
  -H "Authorization: Bearer $MULTISIG_INTEGRATION_KEY" \
  -H "X-MultiSig-Request-Id: <request-id>"
```

For an externally executed Request, wait for `request.status=ready`, then submit its exact `request.mergedXdr` using Stellar Testnet Horizon `POST /transactions` with form field `tx`. Do not submit with MST's Request PUT operation.

If the submission response is lost, use the original Request ID, not a new payment. Discover operation `integration.request.execution.reconcile` in `/operations`. The owning Integration calls:

```sh
curl -sS "https://api-testnet.multisig.tools/stellar/request?view=reconciliation" \
  -H "Authorization: Bearer $MSI_KEY" \
  -H "X-Multisig-Request-Id: $REQUEST_ID"
```

The service checks the stored transaction hash on Stellar and returns one of four outcomes:

| Outcome | Required evidence | Next action |
| --- | --- | --- |
| `unknown` | No terminal evidence | Repeat reconciliation with bounded backoff; escalate if unresolved. Never create a replacement. |
| `successful` | `observation` with transaction hash, ledger, timestamp and `successful: true` | Retain the receipt and close the original payment. |
| `failed` | `observation` with `successful: false` | Review the observed failed execution before separately authorizing any replacement. |
| `not_included` | `nonInclusionProof` covering the entire signed validity window | Review the proof before separately authorizing a replacement. |

A Horizon 404, local expiry, or changed account sequence is not proof of non-inclusion. New prepared Classic payments and CreateAccount transactions carry signed lower and upper time bounds. If imported or older XDR lacks a finite lower/upper bound, or RPC history no longer covers that window, the result can remain unknown and requires manual reconciliation. A Fee Bump receipt includes the actual ledger envelope hash when it differs from the original transaction hash.

Terminal observations and proofs are retained by MST. Ordinary GET Request and Integration webhook projections expose `executionOutcome` independently of the approval state. `submission` is reserved for confirmed success. Check the stored transaction hash against the evidence and retain the original business reference.

If a webhook is configured, treat it as a wake-up signal: verify the signature, deduplicate the event id, then GET current canonical state before acting.
