---
title: Soroban integration
description: Create semantic contract Intents, collect AUTH, and keep execution bound to configured policy.
---

Soroban Integration starts from contract + method + arguments. MultiSig Tools plans current authorization requirements, keeps detached AUTH separate from the transaction shell, and prepares execution only after authorization is ready.

## Choose an available executor

Inspect `GET /runtime-config` before creating a profile. When `capabilities.sorobanManagedExecution.testnet` is false, choose external execution and configure at least one allowed G-account executor in `sorobanExecutionAccounts`. An explicitly selected executor must belong to that pool. A profile or new Intent without an available execution route is rejected with HTTP 409 (`managed_executor_not_configured`) before collecting AUTH. Existing Intents with unavailable execution report `execution_unavailable` in their job projection; do not retry preparation until the execution configuration is corrected.

If the returned execution policy has no bound executor, supply an allowed `executor` when calling `prepare_execution`. When no managed executor is available, omitting this selection returns HTTP 400 (`executor_required`).

A successful observed execution is terminal for the Intent, even if the receipt refers to an earlier authorization revision. Preparation, re-planning and new authorization writes are then rejected with HTTP 409 (`intent_already_executed`). Reconciliation remains available for already released transactions.

A released execution package stays unresolved until its exact hash has a verified result or verified non-inclusion. Do not refresh or re-plan merely because the local time bound elapsed, a submission timed out, or Horizon returned 404. Those operations return HTTP 409 (`intent_execution_outcome_unknown`). Reconcile every hash in `unresolvedTransactionHashes` first. Reconciliation reports `outcome` as `successful`, `failed`, `not_included`, or `unknown`. Non-inclusion requires a healthy Stellar RPC with retained history covering the preparation ledger through a ledger closed strictly after the transaction's time bound, and a subsequent NOT_FOUND lookup. Missing history leaves the outcome unknown. Safe preparation and re-planning require transactional PostgreSQL storage.

Integration owners and Intent creators can inspect a persisted successful receipt without a live ledger lookup. The completed authorization projection does not return reusable authorization entries.

## Create the Intent

For new machine-created semantic Intents, replay the same accepted input and `Idempotency-Key` to recover the existing Intent without reloading its contract interface. Object member order does not matter; changed argument values or types, or changed business context, conflict. Legacy Intents and claims without an accepted-input fingerprint still use their original typed-digest verification, which may require the ABI. Reading current authorization for a pending Intent can still require live signer/ledger state. A stored successful receipt remains available independently of that state.


```bash
curl -sS -X POST https://api-testnet.multisig.tools/stellar/intent \
  -H "Authorization: Bearer $MULTISIG_INTEGRATION_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: contract-test-001" \
  -d '{
    "network": "testnet",
    "contractId": "CA3D5KRYM6CB7OWQ6TWYRR3Z4T7GNZLKERYNZGGA5SOAOPIFY6YQGAXE",
    "method": "transfer",
    "arguments": {
      "from": "GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAWHF",
      "to": "GDGV7V7UT3XDMQ3COT25VCQNJDW57WYPHSLFSAJEW2LLZDCDREWNAPXO",
      "amount": "1"
    }
  }'
```

## Protocol 30 addresses

Use a C address for `contractId`. For a contract argument declared as `MuxedAddress`, the guided input accepts G, C, M and W addresses. A plain `Address` argument does not accept M or W. The W address is a contract destination plus a 64-bit routing ID, not a signing identity. MultiSig Tools preserves the full W address in the reviewed invocation and treats any change to the transfer or mint event's `to_muxed_id` as a change of destination requiring reauthorization. Classic and existing Soroban signer permissions are unchanged.

## Lifecycle

1. Create the Intent inside the Integration Profile's allowed contract/method scope.
2. Collect authorization with Hosted review or a narrow browser capability.
3. Prepare execution after AUTH is ready.
4. Compare final enforcing simulation with reviewed effects.
5. Reconcile the actual ledger result back into the Intent.

## Browser authorization

The owning Integration Service may issue a short-lived capability bound to one service, Intent, AuthorizationPlan revision/digest, signer, exact browser origin, and expiry.

Use the returned `hostedReviewUrl` for human review. Its origin is the network's Hosted website, not the API origin.

The browser can inspect its signer-specific challenge and contribute authorization. It cannot create arbitrary Intents, cancel/replan, change execution ownership, or become a Stellar signer without valid wallet cryptographic evidence.
